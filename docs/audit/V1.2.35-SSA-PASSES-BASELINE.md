# v1.2.35 slice 3 — SSA pass selection (baseline)

Status: **BASELINE**. Owner said "go ahead" after PR #70 merged on
2026-11-28. This is the last deferred slice of v1.2.35.

## 1. Measured current state

- `pkg/ir/ssa/pipeline.go` defines `Pass`, `Pipeline`, `NewPipeline()` with
  `mem2reg → fold-const → cse → dce → licm → sroa`, fixpoint iteration (max 10)
  and `RunWithStats`. It is exercised only by `pkg/ir/ssa/passes_test.go`.
- `grep` for `NewPipeline(` across the repository finds **no production
  caller**: codegen emits IR and applies `SimplifyCFGPass{}` directly at
  `pkg/codegen/emit_ir.go:342`. So a user-visible `--profile` currently changes
  **only the gcc optimization flag**, not the IR passes.
- Slice 1 (`--profile dev|release|size`) is complete and gated; its evidence
  explicitly defers pass selection.

## 2. Scope of this slice

1. Add `ssa.NewPipelineForProfile(profile)` and `Pipeline.PassNames()` so pass
   selection is explicit and inspectable.
2. Wire `pkg/codegen/emit_ir.go` to use the selected pipeline: `dev` keeps the
   existing single `SimplifyCFGPass` call **byte-for-byte**; `release` and
   `size` run the fuller pipeline.
3. Gate: pass-name sets per profile; identical program stdout under every
   profile; byte-determinism within a profile; `dev` output unchanged from the
   pre-slice behavior.

## 3. Boundaries

- No claim that the optimizer makes programs faster. Speed claims require
  measurements and are not part of this slice.
- No change to the native backend, the C23 link flags, or the profile flag UI.
- Existing gates that do not pass `--profile` keep the `dev` path, so their
  emitted bytes must not move. This is the primary regression risk.

## 4. Evidence rule

The gate must compare *pass names* and *observable output*, not just assert
that a function exists. A pipeline that silently runs no passes would satisfy
a weak test; explicit names plus a behavioral corpus do not.

## 5. Evidence and a measured correction

- `ssa.NewPipelineForProfile` and `Pipeline.PassNames` make selection explicit.
  `dev` selects **zero** profile passes, so the historical
  `FoldConstants → SimplifyCFG → DCE` sequence is untouched byte-for-byte.
- First implementation used `NewPipeline()` for `release`, which includes
  `mem2reg`. The gate caught a real miscompile: release/size printed **empty
  stdout** where dev printed `42`. This matches Phase 141's recorded verdict
  that Mem2Reg stays unwired. Fixed by excluding it from both profiles.
- Final pass sets: `release` = fold-const, cse, dce, licm, sroa, simplify-cfg;
  `size` = fold-const, dce, cse, licm, sroa, dce, simplify-cfg (DCE twice).
- Gate `pkg/cli/phase_v1235c_passes_test.go` (`TestPhaseV1235C_`): all tests
  PASS in 49.559 s — explicit pass names (with a `mem2reg == 0` assertion),
  byte-deterministic generated C per profile, and identical `42` output under
  dev/release/size. CI step wired; `go vet` and `go build ./...` clean.
- No speed claim. The optimizer now runs under release/size, but no timing
  comparison is asserted by this gate.
