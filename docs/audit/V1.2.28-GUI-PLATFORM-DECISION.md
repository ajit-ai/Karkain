# v1.2.28 — GUI platform decision (first slice)

Status: **COMPLETE for the capability decision**; no GUI runtime is claimed.

## Decision

| Target | GUI surface | Evidence |
|---|---|---|
| `native-x86_64-*` (C-free) | **Refused by name** with `error[K145]` naming the missing windowing backend; no image is written | `TestPhaseV128_NativeGUIRefused` |
| C23 path, Go and kcc engines | `gui_available()` compiles, links and returns `false` | `TestPhaseV128_C23CapabilityBothEngines` |
| WASM | Out of scope (K108 boundary unchanged) | unchanged |

`gui_available()` is a **capability probe, not a GUI**. It returns `false`
because no GUI backend is linked in this slice. Implementing a windowing
backend (Win32 on Windows, GTK/SDL2 on POSIX) is the next slice; until then the
false result is the honest answer. A negative control proves an unknown
function is not misreported as a GUI boundary
(`TestPhaseV128_UnknownFunctionNotMisreported`).

## Rationale

The native runtime has only `write` and `exit` syscalls — there is no
windowing/event-loop layer to lower GUI calls onto, exactly as for sockets
(v1.2.10) and atomics (v1.2.13). Naming that boundary at check time is what
lets a caller distinguish "this target has no GUI" from "this program is
invalid". The C23 path keeps the `std.gui` capability surface; the real
ImGui/GTK FFI binding is deliberately deferred rather than faked.

## KIR pin

This slice edits `src/compiler/{checker,sema,codegen}.kark`, so the whole-tree
KIR pin will move. It is **not predicted locally**; CI must re-measure it.
