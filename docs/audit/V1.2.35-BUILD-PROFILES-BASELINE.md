# v1.2.35 — optimization/build profiles (baseline)

Status: **BASELINE** — gate to be written against this state. Owner authorized
this slice on 2026-11-27 after PR #66 merged. `proposed` → `in-progress`.

## 1. Measured current state

- `cmd/karkain/main.go` has **no** `--profile` flag and no profile help text.
- `codegen.Config` (`pkg/codegen/codegen.go:20-37`) has `OutputPath`,
  `CompileOnly`, `Verbose`, `RunAfter`, `Debug`, `Target`, `DisableSSA`,
  `Profiling`, `Coverage`, `Trace`, `Stdout`, `Stderr` — **no profile field**, so
  there is no way to ask for an optimization level.
- The C23 link flags are hard-coded to `-O0` in 15 places in
  `pkg/codegen/cross_target.go` (lines 128, 140, 161, 187, 193, 208, 218,
  255, 273, 280, 289, 301, 311, 322); WASI keeps its historical `-O2`.
  `pkg/cli/kcc_engine.go:446,871` passes no optimization flag at all, so gcc
  uses its implicit `-O0`.
- Step M (`docs/audit/STEP-M-COMPILE-RUN-MEASUREMENT.md`) measured the warm
  default C23 path at **1975 ms** median and native at **191 ms**, with exactly
  one gcc call on the C23 paths and zero on native.

So the user has no control over build profiles today, and the compile-time cost
identified by Step M cannot be tuned.

## 2. Scope of this slice (bounded)

1. A user-visible `--profile dev|release|size` flag on `karkain build`/`run`,
   with `dev` as the **default so all existing behavior is preserved**.
2. `Config.Profile` plus one central flag helper, replacing the hard-coded
   `-O0` in the Go C23 link paths (`-O0` / `-O2` / `-Os`) and adding the flag
   to the kcc-engine link path.
3. A gate that, for each profile, uses a gcc PATH shim to **assert the actual
   flag reaches gcc**, verifies the program's stdout is unchanged, checks
   byte-determinism for a repeated build under the same profile, and rejects
   an unknown profile with a usage exit.
4. Benchmarks recorded from the gate, not promised in advance.

## 3. Explicitly NOT in this slice

- **Making native the default for supported programs.** That changes the
  observable behavior of almost every existing gate and needs its own baseline
  and gate. It remains a follow-up within v1.2.35 and is not silently folded
  into this one.
- Pass selection inside the SSA optimizer: the repo already has a pipeline
  (`pkg/ir/ssa`, Phase 94), but wiring a user-visible subset of passes needs a
  separate evidence set and is deferred here.
- Any change to the native backend, bootstrap proof, or v1.2.34 WIP.

## 4. Portability requirement

The profile flag and the gcc shim gate must work on Windows, Linux and macOS.
Shims are `.cmd` on Windows and executable `#!/bin/sh` scripts on POSIX (the
NAT-QUAL lesson: a `.cmd` file is invisible to `LookPath` on POSIX). BSD has no
runner, so no execution claim is made for it.

## 5. Evidence rule

No speed claim until the gate produces numbers. `dev` must remain byte-for-byte
equivalent to today's output; a profile that changes program output is a defect,
not an optimization.

## 6. Evidence (post-change)

- Gate `pkg/cli/phase_v1235_profiles_test.go`, `TestPhaseV1235_`: the unfixed
  tree rejected nothing (an unknown profile was silently ignored and the
  legacy `build` path never invoked gcc with any optimization flag).
- Fixed tree: both tests PASS in 42.254 s. Unknown profile exits with a usage
  error that names the bad value and produces no executable. Each of
  `dev`/`release`/`size` reaches gcc with `-O0`/`-O2`/`-Os` respectively, and
  all three print identical stdout (`hello profiles`).
- The gcc PATH shim is the positive control: the log is non-empty on the
  profiled paths and contains the *expected* flag, which binary-size probing
  could not establish.
- Mutation: making `ProfileOptFlag` always return `-O0` failed exactly the
  `release` and `size` cases with the observed gcc command, while `dev` stayed
  green. The file was restored byte-identically.
- Portability: shims are `.cmd` on Windows and executable `#!/bin/sh` scripts
  on POSIX; the gate selects a same-machine triple from `runtime.GOOS`.
- Timings logged by the gate (12.6 s / 4.0 s / 2.6 s on this host) are **not**
  a performance result: the first path includes CLI construction and the host
  was at 595–644 MB free, inside the documented gcc-kill class. No speed claim
  is made from them.
- CI step *Run v1.2.35 build-profile gate* wired in the same commit.
- KIR pin unchanged: no `src/compiler/*.kark` file was modified in this slice.

## 7. Deferred within v1.2.35

Making the native path the default for supported programs, and selecting
individual SSA passes, were deliberately not part of this commit (§3). Both
later landed as their own baselines and gates:
`V1.2.35-NATIVE-DEFAULT-BASELINE.md` and `V1.2.35-SSA-PASSES-BASELINE.md`.
The profile flag itself is available on both C23 engines (Go codegen link
flags and the kcc-engine link path).

## 8. First-CI corrective — POSIX shim quoting

CI's Linux leg failed all three profile cases with logs containing only the
literal text `gcc $*`. The compiler was correct: the program printed
`hello profiles` under every profile. The **gate's POSIX shim** wrote the
argument list inside single quotes, which `/bin/sh` does not expand; the
Windows `.cmd` shim expanded `%*` correctly, so the defect was visible only
on Linux. Fixed by writing `echo "gcc $*" >> '<log>'` with double quotes.

Verified by executing the generated script under Git's `sh`: the log recorded
`gcc -O2 hello.c -o hello.exe`. The full gate then passed locally (52.469 s).
No compiler source changed; the KIR pin stays 20494. This is recorded rather
than hidden because an empty/misleading shim log is precisely the class of
"evidence" that can make a gate vacuous.
