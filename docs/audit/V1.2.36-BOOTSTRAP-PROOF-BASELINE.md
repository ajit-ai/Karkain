# v1.2.36 — bootstrap closure proof (baseline)

Status: **IN PROGRESS — verification attempt**. Owner authorized this slice on
2026-11-27 after PR #65 merged. `proposed` → `in-progress` in the v1.2.x queue.
This is a **verification** slice: no language or compiler feature is added, and
no closure condition is upgraded without a passing gate.

## 1. Objective and exit criteria

Prove the remaining self-hosting claim of increment 154:

- `TestPhase154_PinRetired` runs with `KARKAIN_SEED_CLOSURE=1`;
- stage 1 is the known Go seed build, but stages 2 and 3 run compiler children
  with the Go pin retired;
- `stage2 == stage3` bitwise with a **non-zero** byte count;
- `CompilerChildEnv()` contains no `KARKAIN_ENGINE=go`;
- the witness line is present: `phase154 witness: pin RETIRED, stage2 == stage3
  bitwise identical (N bytes)` with `N > 0`.

The fast half, `TestPhase154_PinMechanism`, is already green in the required CI
`Test` job (0.09 s, mutation-verified M1/M2). It proves the pin contract, not
the three-stage closure. Both siblings — `TestPhase154_ControlPinActive` and
`TestPhase154_NoGoEnginePin` — remain **unproven** unless run separately; a
passing `_PinRetired` must not imply them green.

## 2. Known blockers (recorded before attempting)

- This host is windows/amd64 with roughly 200–900 MB free against the Phase 127
  `error[K127]` threshold of 1536 MiB. The guard is expected to refuse stage 2
  with a clean diagnostic.
- With the guard overridden (`KARKAIN_BOOTSTRAP_MIN_MEM=0`), prior sessions
  recorded the stage-2 transpile dying with `exit status 1` — a host capacity
  limit, not a compiler defect (`PHASE-154-BASELINE.md` §8).
- GitHub-hosted runners kill the same step with `exit 143` about 110 s in, with
  no witness line even unbuffered (REL-002 / B2 class). The `phase154-closure`
  job is therefore `schedule` + `workflow_dispatch` only and is not a required
  check; it treats a SKIP as a failure.
- A concurrent v1.2.34 WIP in the working tree (`pkg/codegen/codegen.go` plus
  four `stdlib/*.kark` files) currently breaks `go build ./...`. Verification
  is therefore run in a clean detached worktree at HEAD, leaving that work
  untouched.

## 3. Portability requirement

The owner's explicit concern: Karkain is developed on Windows but must work on
Linux, macOS and BSD. This slice therefore adopts the repository's existing
platform discipline:

| Platform | Existing bootstrap evidence | What this slice may claim |
|---|---|---|
| Windows | host-side stage builds are the only local evidence | only what runs here |
| Linux | `ubuntu-latest` CI leg executes ELF and the required `Test` job runs the fast pin contract | CI-measured results only |
| macOS | `macos-13` job is `workflow_dispatch`-only; x86-64 only | no automatic proof |
| FreeBSD / BSD | v1.2.30 added target **models** only; no runner | **unproven — must say so** |

A Windows pass is never presented as a cross-platform bootstrap proof. A CI
`exit 143`, a `--- SKIP:`, or a zero-byte witness is a failure or an unmet
condition, never a pass. No condition is marked satisfied unless its own gate
produced evidence on the relevant host.

## 4. Measured result (2026-11-27, windows/amd64)

Verification ran in a clean detached worktree at `f8092da`, so the concurrent
v1.2.34 WIP in the main working tree was neither used nor changed.

- `TestPhase154_PinMechanism`: **PASS** in 0.19 s (package 1.708 s). The pin
  contract is real; this is the fast half already in the required CI job.
- `TestPhase154_PinRetired` with `KARKAIN_SEED_CLOSURE=1`:
  - Stage 1 succeeded: `karkain-compiler1.exe`, 4,939,719 bytes, SHA prefix
    `7d3d2ab2f67a7595`, in 46.98 s.
  - Stage 2 was refused by the K127 guard before any compiler child ran:
    `error[K127]: cannot run bootstrap stage 2: only 890 MiB memory available,
    1536 MiB required`.
  - Result: `--- SKIP: TestPhase154_PinRetired (47.00s)`, package PASS.
  - **This is not a proof.** The gate deliberately treats a skip as a failure
    of the closure claim, even though `go test` exits 0.
- A second attempt with `KARKAIN_BOOTSTRAP_MIN_MEM=0` was started to measure
  what the host does with the guard disabled, but the **shell was cancelled by
  a server restart before producing output**. There is no result from that
  attempt and none is inferred here.

**Verdict: v1.2.36 UNMET.** Closure conditions 5 and 6 remain open. Host free RAM
at the check was 890 MiB; total 4005 MiB. No `stage2 == stage3` witness with a
non-zero byte count exists on this host.
