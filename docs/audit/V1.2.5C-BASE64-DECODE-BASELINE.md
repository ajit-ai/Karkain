# v1.2.5c - native base64_decode_bytes (baseline and evidence)

Date: 2026-11-22
Branch: feature/v1.2.5c-base64-decode
Baseline: develop 3d8c849 (PR #26: v1.2.5b, KIR pin 16841)

## Scope
Lower base64_decode_bytes in the kcc native driver: 88-byte frame, arithmetic
(nibble-equivalent) base64 value decode instead of the oracle's 256-byte table,
two independent padding checks, and two distinct runtime-error messages.

## Blocker found and fixed in this slice
The kcc PE writer (src/compiler/native_pe.kark) hardcoded section RVAs
.text=0x1000, .idata=0x2000, .reloc=0x3000. With hex and base64-encode helpers
.text SizeOfRawData was 0xff1 (one byte under a page); adding base64-decode
pushed it past 0x1000, so .idata's fixed RVA overlapped .text and the oracle's
ParsePE rejected the image ("unexpected .idata layout"). The writer now
computes idataRVA and relocRVA from the aligned text/data sizes, matching the
oracle's dynamic section placement. No C23 dependency added.

## Boundary
NUL-containing decoded bytes cannot be compared with the C backend (C strings
truncate at NUL); the corpus uses printable vectors. No byte-identity with the
Go oracle claimed (contract is the decoded VALUE).
