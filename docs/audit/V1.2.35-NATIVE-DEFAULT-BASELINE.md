# v1.2.35 slice 2 — native as default for supported programs (baseline)

Status: **BASELINE / DESIGN GATE**. No code changed. This slice was deferred
from slice 1 (`docs/audit/V1.2.35-BUILD-PROFILES-BASELINE.md` §3/§7) to its own
baseline and gate. Host at measurement: windows/amd64, **129 MB free RAM**.

## 1. What "default" means today

`codegen.NewConfig()` sets `Target: "native"`, but that is the **legacy alias**
for the C23 transpile path, not the C-free machine-code path (`commands.go:32-106`):
`RunCommand` only enters `cfreeRunForOS` when `IsNativeTarget(cfg.Target)` is
true, i.e. an explicit `native-x86_64-<os>` target. So a plain `karkain run`
always compiles C23 and calls gcc.

## 2. Measured support boundary (2026-11-28)

`docs/inventory/native-feature-matrix.json` has **42 supported** and
**28 not_supported** rows. Direct CLI measurements with a freshly built kcc:

| Program | `--target native-x86_64-windows` | Result |
|---|---|---|
| `examples/01-fundamentals/01_hello_world.kark` | accepted | prints `Hello, Karkain!`, exit 0 |
| `examples/stdlib/os/main.kark` | refused | `error[K145]`: string argument for int parameter `msg` (call to `log_info`) |
| `examples/01-fundamentals/13_enums.kark` | refused | `error[K145]`: `let a` initialised from a non-integer expression |

So "supported" cannot be inferred from the file's extension or from a simple
syntax check. The **native driver's own scan and plan** is the only authority
on whether a program can be lowered.

## 3. Why a naive default flip is not acceptable

Changing the default target to `native-x86_64-<os>` unconditionally would turn
every stdlib or enum program into a hard failure. Adding an automatic retry on
`error[K145]` would be a **silent target switch** — the same class of dishonesty
the 151D seam was created to end (an image would appear without the user
knowing which backend produced it). Neither is acceptable.

## 4. Design required before implementation

1. Add a non-emitting support probe to the self-hosted driver — e.g.
   `kcc native-check <file.kark> --target <native-target>` — that runs the same
   scan/plan as `natNativeProgramOS` and prints a single machine-readable
   verdict: `[ok] native supported` or `error[K145] native target: <reason>`.
   It must never emit or write an image.
2. In `karkain run`/`build` with **no explicit `--target`**, call that probe.
   On `supported`, select the host's native target and print a verbose line
   naming the choice; on refusal, keep the historical C23 path and print the
   same verbose reason. With an explicit `--target`, today's behavior is
   unchanged byte-for-byte.
3. Gate: (a) hello program defaults to native and executes with exact stdout;
   (b) stdlib/enum program defaults to C23 and still prints its golden output;
   (c) explicit `--target c23` and explicit native target are untouched;
   (d) the probe never writes an image; (e) PATH shims prove no gcc on the
   native-default path and a real gcc call on the C23-default path.

## 5. Host constraint

The stage-1 build of kcc needs roughly 1.5 GiB of headroom on this machine
(the Phase 127 class); only 129 MB was free at baseline time. Implementation
and gate execution should be scheduled when memory is available rather than
forced with `KARKAIN_BOOTSTRAP_MIN_MEM=0`. No claim will be made from an
unverified build.

## 6. Not in this slice

SSA pass selection remains deferred. v1.2.32 (REL-001) and v1.2.33 (security)
are separate authorized slices; v1.2.36 remains blocked on the 8–12 GB machine.

## 7. Evidence (post-implementation)

- `src/compiler/main.kark` gained `kcc native-check <file> --target <native-*>`:
  it runs the same assemble/tokenize/parse/type-check/scan/plan as a real build
  and prints only `[ok] native supported` or the `error[K145]` reason. It never
  emits or writes an image (gate asserts no `.exe`/`.c23` appears).
- `cmd/karkain/main.go` tracks whether `--target` was explicit. For `run` under
  the kcc engine with no explicit target, it asks `cli.KCCNativeSupported`; on
  success it selects the host's native target and reports the choice under
  `--verbose`. A refusal keeps the historical C23 path. Explicit targets are
  untouched byte-for-byte.
- `pkg/cli/phase_v1235b_native_default_test.go` (`TestPhaseV1235B_`): all four
  tests PASS in 65.012 s with a fresh CLI and kcc — native default for a simple
  program (gcc shim log empty), C23 default for a stdlib program (log non-empty),
  explicit c23/native paths unchanged, and the probe writes no artifact.
- `go vet` and `go build` clean. The one gofmt difference in `main.go` is the
  pre-existing line-757 struct-tag alignment, verified unchanged at HEAD.
- KIR pin deliberately not predicted: `src/compiler/main.kark` changed, so CI
  must re-measure `text=N verify=N` from its own Phase 122 job.
- Host note: the gate ran when free RAM rose from 129 MB to 346 MB; no guard was
  disabled and no forced pass was used.

## 8. First-CI corrective — trait/impl bridge on the native path

CI failed the pre-existing v1.2.26 trait gate (`TestPhaseV1226F_`) with a
5-minute `kcc run timed out`, reproduced locally (316 s). Bisection showed:

- explicit `--target c23` on the trait program returns `42`;
- explicit native and the new implicit default both hang;
- `kcc native-check` on raw trait syntax hangs, while the same source after
  `applyKCCBridge` returns `[ok] native supported` and builds/executes a PE
  printing `42`.

Root cause: the **native CLI path** (`pkg/cli/kcc_native.go`) staged sources
with `kccStageInput` but never called `applyKCCBridge`, unlike the C23 kcc
path. kcc's parser therefore received raw `trait`/`impl` text. Fixed by
applying the bridge at both native staging sites (build and run), and by
making `KCCNativeSupported` stage+bridge before probing. Added a regression
case `TestPhaseV1235B_TraitProgramUsesBridgeOnNativeDefault` so this class is
caught by the native-default gate itself.

Verified: `TestPhaseV1226F_` and all `TestPhaseV1235B_` cases PASS together in
71.860 s with a fresh CLI and kcc. No compiler source changed; KIR pin stays
at the CI-measured 20938.
