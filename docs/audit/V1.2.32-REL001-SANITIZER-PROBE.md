# v1.2.32 — REL-001 sanitizer investigation (verification, blocked)

Status: **VERIFICATION ATTEMPTED — TOOLCHAIN BLOCKED**. No code changed.
`REL-001-CRASH-INVESTIGATION.md` remains the authoritative record of the
original negative result; this note adds the 2026-11-28 toolchain probe.

## 1. Objective

The authorized experiment named in `REL-001-CRASH-INVESTIGATION.md`: build
the self-hosted compiler with a sanitizer and run the whole-tree
`kir --verify` to classify the intermittent kcc `0xC0000005` (empty output,
exit 3). Earlier work falsified the low-RAM, stack-exhaustion and
corrupt-binary hypotheses and recorded five consecutive clean runs, so the
finding stayed **UNCLASSIFIED** — not fixed, not intentional, not stale.

## 2. Measured toolchain availability (2026-11-28, windows/amd64)

| Item | Result |
|---|---|
| `gcc --version` | `gcc.exe (Rev7, Built by MSYS2 project) 16.2.0` |
| `gcc -fsanitize=address` on a 1-line C program | **fails**: `ld.exe: cannot find -lasan` (exit 1) |
| `gcc -fsanitize=undefined` on the same program | **fails**: `ld.exe: cannot find -lubsan` (exit 1) |
| `clang` on `PATH` | absent |
| `C:\msys64\clang64\bin` | directory exists but contains no `clang.exe` or ASan runtime |
| Free RAM during probe | ~290 MiB |

The earlier investigation reached the same `-lasan` failure with gcc 14.2.0;
this probe confirms it with the current 16.2.0 toolchain and additionally
rules out UBSan and the locally installed clang directory. Installing a
sanitizer runtime is a system-level change and was **not** performed.

## 3. Earlier decisive experiment already recorded

`REL-001-CRASH-INVESTIGATION.md` §2–§4 built two isolated kcc binaries from
the same generated C, one with the repository's exact flags and one with
`-Wl,--stack,67108864`. PE header inspection confirmed `SizeOfStackReserve`
2 MiB vs 64 MiB. Both binaries and the control completed cleanly
(466 / 608 / 473 / 487 s) with identical 61-byte output. So the stack
hypothesis was tested and rejected on evidence, not assumed.

## 4. Verdict

**REL-001 remains UNCLASSIFIED.** The sanitizer experiment cannot run on this
host because no ASan or UBSan runtime is installed for any available compiler.
This is a toolchain limitation, not a compiler defect and not a pass. No gate
was weakened and no claim was upgraded.

## 5. Exact experiment for a capable host

On a machine with a compiler that ships ASan (for example a full LLVM/Clang
install or an MSYS2 environment with `mingw-w64-clang-x86_64-runtime`):

```text
# 1. generate C from the compiler sources with the Go front end
KARKAIN_ENGINE=go karkain build src/compiler/main.kark

# 2. build an instrumented kcc OUTSIDE the repository
clang -std=c99 -D_POSIX_C_SOURCE=200809L src/compiler/main.c \
  -o <temp>/kcc-asan.exe -fsanitize=address -lgmp -lm -lws2_32

# 3. run the exact failing workload, isolated and unbuffered
KARKAIN_KCC=<temp>/kcc-asan.exe \
  go run ./cmd/karkain kir --verify src/compiler/kir.kark
```

Acceptance: a sanitizer report names the offending access and its source
line; a clean run is another negative result, not a classification. The
result must be recorded here before any fix is authorized — a finding is not
implementation authority.
