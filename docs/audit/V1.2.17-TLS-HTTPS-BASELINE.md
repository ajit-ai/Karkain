# v1.2.17 — C23 TLS/HTTPS on both engines

**Verdict: COMPLETE for the C23 path.** Both the Go front end and the
self-hosted kcc engine perform a real TLS handshake and return the decrypted
HTTP body through `https_get` / `https_post`. Native and WASM remain
C23-excluded by the v1.2.10 platform decision (no socket syscalls).

## 1. Measured baseline

- No transport TLS existed anywhere in shipping code: `stdlib/net/net.kark`
  and `stdlib/http/http.kark` used plain `net_*` TCP only; no
  TLS/HTTPS/SSL/OpenSSL references existed in SPEC, stable-api, feature
  matrices or runtime helpers. The unrelated `PE TLS` records mean
  thread-local storage, not transport security.
- `http.get` in Go codegen was a hardcoded placeholder
  (`"HTTP GET response (placeholder)"`), not network I/O.
- The seven `net_*` builtins are registered and emitted on both engines;
  `pkg/native` refuses them with K145 (v1.2.10), and WASM has none.
- Host libraries measured on windows/amd64: MinGW has
  `libwinhttp.a`, `libsecur32.a`, `libcrypt32.a` and `winhttp.h`; it has **no**
  `openssl/ssl.h`, `libssl.a` or `libcrypto.a`. Therefore Windows uses WinHTTP
  (Schannel underneath) and POSIX uses OpenSSL.
- `KARKAIN-VERSION-PLAN.md` NFR-11 and `KARKAIN-INDEPENDENCE-ROADMAP.md`
  previously listed TLS as Planned because of the no-C-dependency rule. The
  owner authorized this C23 platform-adapter scope for v1.2.17 after the
  dependency tradeoff was presented (2026-11-25).

## 2. What changed

### Runtime (single source of truth)
- `runtime/tls/c/karkain_tls.h`, `runtime/tls/c/karkain_tls.c`:
  `karkain_https_request(method, host, port, path, body, verify)` and
  `karkain_tls_last_error()`. WinHTTP path performs SNI, chain and hostname
  verification by default; `verify=0` sets the four explicit
  `SECURITY_FLAG_IGNORE_CERT_*` flags for loopback self-signed servers while
  the connection remains encrypted. POSIX path uses `SSL_CTX_new`,
  `X509_VERIFY_PARAM_set1_host`, `SSL_set_tlsext_host_name`, and reuses the
  existing `karkain_net_connect` socket.
- Both paths normalize the response to the entity body (strip `\r\n\r\n`
  headers from OpenSSL's raw stream) so engines print identical bytes.
- `runtime/tls/embed.go` embeds the C files for the Go engine;
  `scripts/gen-tls-runtime.ps1` generates `src/compiler/tls_runtime.kark` for
  kcc. `pkg/codegen/tls_kark_fresh_test.go` (`TestTLSKarkFresh`) pins the
  generated mapping. The generated file is never hand-edited.

### Builtins and generation
- `https_request` (6 args) and `tls_last_error` (0 args) added to the Go
  resolver, both kcc checker/sema tables, both C dispatchers.
- `needsTLS` prescan gates emission: a TLS-free program (including the
  bootstrap compiler) emits no TLS runtime and keeps its historical link
  flags. `pkg/codegen/tls_runtime.go` carries the prescan, embed and
  `TLSLibFlags` helper.
- Link libraries are added only when the generator's `needsTLS` is set:
  `-lwinhttp` on Windows, `-lssl -lcrypto` on POSIX. kcc's three link paths
  append the platform flags unconditionally because the self-hosted compiler
  cannot infer usage there; the libraries are present on both CI legs.

### Library surface
- `stdlib/http/http.kark`: `https_get(host, port, path, verify)`,
  `https_post(host, port, path, body, verify)`, `https_last_error()`.
  Canonical untyped source so both engines compile it identically.

## 4. Non-claims and boundaries

- **No byte-identity** with the Go native backend: native has no sockets.
  The gate compares observable decrypted stdout, not image bytes.
- **KIR pin re-pinned from CI measurement only.** `src/compiler/{checker,codegen,sema}.kark`
  and the generated `src/compiler/tls_runtime.kark` changed, so the whole-tree
  KIR count moved. Local whole-tree `kcc kir --verify` is in the documented
  crash/OOM class on this host, so no value was measured or predicted locally.
  CI run `45656354614` reported `text=18187 verify=18187`; only that
  measurement re-pinned `phase122_pipeline_ownership_test.go` and
  `phase151a5_win_test.go` (see §6).
- **No native/WASM TLS.** `std.net` remains refused by name on native
  (v1.2.10); the v1.2.13 atomics decision is unchanged.
- **`verify=0` is not a production trust decision**: it disables certificate
  checks for loopback/self-signed tests. It is gated and documented, never
  the default in examples.
- **No HTTP/2, no WebSocket, no proxy, no client certificates, no custom CA
  bundle API** in this increment.
- **No macOS TLS link validation on this host**: the POSIX branch is CI's
  Linux leg; macOS cross builds need an OpenSSL sysroot supplied by `CC`.

## 5. CI

Two dedicated steps are wired in `.github/workflows/ci.yml`:
*Run TLS runtime freshness gate* (`TestTLSKarkFresh`) and
*Run v1.2.17 C23 TLS/HTTPS gate* (`TestPhaseV1217_`). The gate is a test file
plus a CI step, per the repository rule.

## 6. First CI run — three defects, corrected against this baseline

CI run `45656354614` (PR #38, 2026-11-25) found three real defects. This is a
corrective change against the v1.2.17 baseline, not a new increment.

1. **Whole-tree KIR pin was stale.** The CI *kcc whole-tree self-check
   (Phase 122)* job measured `text=18187 verify=18187` against the old
   `17924`. That is the authoritative measurement; both assertion sites
   (`phase122_pipeline_ownership_test.go` and `phase151a5_win_test.go`) were
   re-pinned from it. The +263 delta is the new builtins in
   `checker/sema/codegen.kark` plus the generated `tls_runtime.kark`. No local
   whole-tree verification was attempted and no value was predicted.
2. **Sphinx `-W` failed on `docs/source/status/feature-matrix.rst:249`:**
   `Explicit markup ends without a blank line; unexpected unindent`. The new
   TLS section was appended directly after the previous list-table row. A
   blank line now separates them. Local Sphinx is unavailable on this host
   (`python` not on PATH), so the fix is verified structurally, not by a local
   `-W` run.
3. **The Phase-114 corpus regression broke on imported `std.http`.** The Go
   incremental/split path generates one TU per module but `SplitToolchain`
   has no generator, so the whole-program `needsTLS` prescan result was not
   reflected in the shared header or link libraries. Programs that only
   `import std.http` (and never call `https_request` in the root file)
   compiled module TUs containing `karkain_https_request` with no prototype:
   `implicit declaration of function 'karkain_https_request'` and
   `incompatible types when assigning to type 'Value' from type 'int'`.
   Fixed by carrying `NeedsTLS` in `SplitResult`, appending `tlsRuntimeC()` to
   the shared runtime text, and appending the platform TLS libraries to the
   split link line. The monolith path and the bootstrap compiler are
   unchanged.

**Post-fix evidence:** `TestPhase114_CorpusExamples_GoEngine|TestPhase114_CorpusCoverage`
PASS 581.688 s; `TestPhase114_CorpusExamples_KCCParity` PASS 694.995 s;
`go build ./...`, `go vet ./pkg/... ./cmd/...`, and both runtime freshness

unchanged by the split fix.
