## 2. Scope of this slice

1. A deterministic SBOM generator over the release directory (SPDX-lite JSON:
   product name/version, listed artifacts with SHA-256, no external Go module
   dependencies because `go.mod` declares none). `karkain sbom` exposes it.
2. `SECURITY.md` gains a real CVE response SLA, the supported-version table
   is corrected to 1.2.0, and SBOM/signing availability is stated honestly.
3. A gate proving the SBOM is generated correctly and deterministically, and
   that the policy document actually contains the claimed sections.

## 3. Explicitly out of scope

- **Artifact signing (cosign)** — increment 165, not started. The docs must say
  so rather than imply signed releases.
- **Language-level `unsafe {}` / `requires` annotations** — the capability
  model document says not to implement until a complete model exists. No
  parser or checker change is authorized by this slice.
- Any claim that SEC-001 is fully closed: signing remains open, so the
  honest outcome is "SBOM + CVE SLA delivered; signing carried to 165".

## 4. Evidence rule

No security claim without an artifact or a gate. A documentation sentence is
not a control; the SBOM generator's output is parsed and hash-checked in the
gate. Determinism matters because release artifacts are verified by SHA-256.
