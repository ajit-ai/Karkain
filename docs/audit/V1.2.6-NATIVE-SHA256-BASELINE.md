# v1.2.6 - native sha256_hex (baseline and evidence)

Date: 2026-11-23
Branch: `develop`
Baseline: `caad470` (P0.2 task cancellation and timed joins)
Classification: new capability, codec-family slice.

## 1. What is missing

`sha256_hex(data)` is a language-level runtime builtin: the Go engine lowers it
to `karkain_sha256(...)` in the generated C preamble, and every other codec in
that family (`hex_encode/decode`, `base64_encode/decode`, `sha512_hex`) has a
native kcc helper. SHA-256 is the one that does not, so a native-target program
that imports `std.crypto` cannot build.

This matters beyond the function itself: `std.crypto` is the module the
`stdlib_v2` and `std.net` no-C closure conditions (carried to v1.3.0) depend on,
and a module cannot be built without a C compiler while one of its two entry
points has no native lowering.

## 2. Contract

`sha256_hex(s string) -> string`

* Returns the SHA-256 digest of the string's bytes as **64 lowercase hex
  characters**, exactly as the C runtime's `karkain_sha256` does.
* The digest is over the string's length-delimited bytes, not a NUL-terminated
  buffer; the two coincide for every literal, and the length form is what the
  native value model carries.
* Known vectors the gate asserts (NIST FIPS 180-4 and the repository's own):
  - `""` -> `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`
  - `"abc"` -> `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`
  - `"karkain"` -> `00e0cba20c10cac449eb885a9926a4b646f0ac163ed7fbc5704d9d8a057ef44d`
* The result is always 64 printable ASCII bytes, so unlike the decode codecs it
  can be compared with the C backend byte for byte and has no NUL boundary.

## 3. Design

The oracle is the C implementation in `pkg/codegen/codegen.go`
(`karkain_sha256`), which is the correctness definition; this slice reproduces
its **output**, not its instruction sequence.

* **32-bit word arithmetic.** SHA-256 is defined over `uint32` with wrapping
  addition. The native driver's ALU primitives are 64-bit, so this slice adds
  the 32-bit register forms (`mov/add/sub/and/or/xor/shl/shr` with a zero `w`
  bit in REX). Writing a 32-bit register zeroes its upper half on x86-64, so
  every intermediate is canonical with no masking pass.
  No new opcode selectors are required: `0x89/0x01/0x29/0x21/0x09/0x31/0xC1`
  already exist in the shared table; the forms differ only in the REX.W bit.
* **Message schedule and round constants in the helper frame.** Karkain cannot
  embed an arbitrary byte-string literal (the same limit that made hex decode
  arithmetic), so the 64-entry K table is materialised in the helper's frame
  once at entry from `mov r64, imm64` immediates, and the 64-entry W schedule
  lives beside it. Both are indexed by the loop counter.
* **Padding without a second buffer.** The C oracle allocates `pad` and copies
  it after the message; the helper computes each block byte on the fly from
  `(index < len) ? msg[index] : padByte(index - len)`, where `padByte` is
  `0x80` at offset 0, a big-endian length byte in the final eight, and zero
  elsewhere. This keeps the helper's only allocation the 64-byte output.
* **Output is allocated in the arena** and written in place; the hex digits are
  computed arithmetically (`'0'+n` or `'a'+n-10`), so no 16-byte alphabet has to
  be interned and no rodata reference is recorded by this helper.
* **Call path** reuses the existing `codecTemp` staging the other codecs use,
  with the oracle's `(ptr, len)` string convention.

## 4. Evidence plan

* **Exact-bytes PE execution** on this Windows host for every vector above plus
  a length that crosses a block boundary, a 55/56/64-byte padding boundary
  triple (the `0x80` plus length-only block case), and a multi-block message.
* **C-backend differential**: the same source compiled and run through the Go
  engine, compared byte for byte. This is the semantic authority; the two
  engines agree on the digest, which no golden invented here could establish.
* **Runtime-error and refusal rows**: a non-string argument is rejected by the
  checker, not by the helper.
* **Determinism and non-vacuity**: repeated builds are byte-identical, and the
  corpus must produce distinct digests so a helper returning a constant cannot
  pass.
* **Mutation verification**: at least one algorithmic change (a rotation
  amount, a round-constant index, or the padding length) must fail both the
  execution layer and the differential, then be restored byte-identically.

## 5. Boundaries stated up front

* **No byte-identity claim with the Go native oracle.** The Go native backend
  DOES have a SHA-256 helper (`pkg/native/sha256.go`, Phase 152-B2), so a
  behavioral native-vs-native differential is available. Byte-identity is still
  not claimed: kcc materialises the K table in the helper frame and uses true
  32-bit ALU forms, while Go uses rodata K/alphabet and 64-bit ops with a
  mask32. The contract is the digest VALUE, proven by execution, by the C
  engine, and by the Go native engine.
* **No streaming/incremental API.** `sha256_hex` hashes one complete string;
  a hashing state object is not part of this slice.
* **No `sha512_hex` here.** It is the natural next codec slice and is not
  implied by this one.
* **No new language surface and no `SPEC.md` change**: the builtin already
  exists in the language definition; only the native lowering is added.

## 6. Result

In progress. The wiring gaps found during implementation are closed:
`sha256_hex` is in `natNativeCodecIn` (so `codecTemp` is reserved and the helper
emission gate fires), in the print/value scan and the return-of-string refusal,
and the arena's fixed 65-byte-per-site cost is ADDITIVE like the Go oracle's.
The duplicate partial helper in `native_value.kark` is removed; the single
implementation home is `src/compiler/native_sha256.kark`. `natRolRegImm32` now
uses the `C1 /0` opcode selector (64), not the group-1 `/5` selector (24).

Gate: `pkg/cli/phase_v126_sha256_test.go` (`TestPhaseV126_`), CI step
*Run v1.2.6 native sha256 gate*. Execution/differential results and the KIR
re-pin are recorded after the focused gate and CI measurement.
