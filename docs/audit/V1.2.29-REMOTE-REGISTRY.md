# v1.2.29 — Remote registry (HTTP)

Status: **COMPLETE for the exposed HTTP registry surface**. What shipped here
is CLI exposure and a hermetic end-to-end gate over an in-process HTTP server;
the underlying v1 HTTP client already existed in `pkg/pm/registry.go`.

## What changed

- `karkain pkg search <query> [--registry <url>]` and
  `karkain pkg info <name> [--registry <url>]` now accept an explicit registry
  URL, not only the `KARKAIN_REGISTRY` environment fallback. The flag is
  applied for the duration of one command and restored afterwards.
- Registry selection was already source-aware in `RegistryRefForDep`: a
  dependency URL or `--registry` beginning with `http(s)://` selects the
  remote client, everything else must be a local Phase-135 directory. That
  split is unchanged — local registries keep their no-network behavior.
- No public registry is contacted: gate `TestPhaseV129_RemoteDiscoveryBothCommands`
  and `TestPhaseV129_RemoteFetchThroughCLI` run an `httptest` server with the v1
  search/metadata/download endpoints and a SHA-256 integrity header.

## Boundaries

`karkain pkg registry init` and `pkg publish` remain **local-only** by design;
remote publishing is not authorized here. Authentication in `pkg/pm/auth.go`
still carries its pre-existing TODO and was not touched. No kcc source changed,
so the whole-tree KIR pin does not move.
