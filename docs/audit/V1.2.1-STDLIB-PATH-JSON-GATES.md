# v1.2.1 — `std.path` / `std.json` cross-engine gates

Status: **COMPLETE for the covered surface** (library slice, branch
`feature/v1.2.1-stdlib-path-json-gates`). This uses the user's numbering rule:
all future library versions are **v1.2.1, v1.2.2, … v1.2.n**. No other version
line is used.

## Why this slice

1. The read-only library assessment found `std.path` and `std.json` present and
   importable on `develop`, but with **no located gate/executed evidence**.
2. `v1.2.x` closure condition 1 names these modules explicitly.
3. The implementation-control document's "next slice" recommendation is stale:
   a real two-argument user function call already builds and executes through
   the C-free native path on this tree, so it cannot be treated as unimplemented.
4. The unmerged native-string branch is a 5,500-line stack and would violate the
   one-slice rule if ported wholesale. This slice takes the small, deterministic
   library-gating work instead.

## Gate

- File: `pkg/cli/phase_v121_stdlib_test.go`
- Pattern: `TestPhaseV121_`
- CI step: *Run v1.2.1 stdlib path/json gates* in `.github/workflows/ci.yml`
- Fixtures live under `.karkain-dev` so stdlib resolution walks to the repo root.
- Each case runs through the real `karkain run --engine go|kcc` pipeline.
- Raw Go and kcc stdout must be byte-identical; the semantic golden normalises
  only CRLF, never the difference between engines.

Measured locally: **PASS** (48.7 s after the final fix).

## Defects found and fixed

Both failures were uncovered by the gate before any library code was changed.

### 1. `std.path`: kcc indexed past the start of a path component

First gate result:

```
runtime error: string index out of range at main.kark:14
  stack:
    path_basename (main.kark:14)
    path_extension (main.kark:30)
    path_stem (main.kark:40)
    main (main.kark:101)
```

Cause: `path_basename` and `path_dirname` used
`while (i >= 0 && path[i] != "/")`. The kcc C path evaluates the indexed
operand before the range guard, so `path[-1]` was reached for a component with
no separator. The fix rewrites those loops — and the related `path_extension`,
`path_has_extension`, `path_replace_extension` and `path_is_absolute` guards —
so the range check is an outer `if` and indexing happens only inside it. The
public surface is unchanged.

Mutation verification: changing `start = i + 1` back to `start = i` in
`path_basename` failed the path case with `/c.txt`, `/c` and `/a/b//c.md`; the
exact fix was restored.

### 2. `std.json`: `json_array_length("[1, 2, 3]")` returned 1

Cause: the loop started at index 1 with `depth = 0`, so the opening `[` was
never counted and no comma ever saw `depth == 1`. The fix starts at index 0,
uses `depth = 1` for the array itself, and counts top-level commas with nested
`if` statements rather than `&&` short-circuiting.

Mutation verification: changing `count = 1` to `count = 0` failed the JSON case
with `2` instead of `3`; the exact fix was restored.

### 3. Wrong gate expectations, corrected rather than blamed on the library

Two early golden mismatches were my expectations, not defects: direct boolean
literals print `true`/`false`, while a `bool`-returning stdlib function result
prints `1` on both engines. The golden now records the measured behavior.

## Boundaries

- This slice does not gate `std.env`, `std.time` or `std.random`; they are
  shell-backed and nondeterministic, and belong to a later v1.2.x slice.
- No compiler source moved, so the whole-tree KIR pin remains **16017** and no
  re-measure was required.
- This does not close no-C native `stdlib_v2`; it establishes executed evidence
  for two deterministic modules named by closure condition 1.
