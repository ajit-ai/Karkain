# v1.2.22 — Real SQLite driver

**Verdict: COMPLETE for the C23 path.** Both front ends can open SQLite
databases (`:memory:` or temp file), execute DDL/DML, run SELECT queries into
Karkain arrays, close handles and report deterministic errors. Native and WASM
remain excluded by existing FFI/socket/toolchain boundaries.

## 1. Measured baseline

- `stdlib/db/db.kark` is a pure-Karkain SQL-text engine (`db2` / `embedded`),
  with immutable map snapshots and a pipe-delimited text format. It has no
  parameter binding, joins, expressions or real database engine.
- No SQLite headers or libraries are installed on the dev host or CI runners;
  CI installs only gcc/gmp. Depending on system packages would make builds
  non-reproducible and require runner changes on Windows and Linux.
- C FFI exists but is thin, and MinGW ignores `#pragma comment(lib, ...)`;
  link inputs must be explicit.
- The 10-second compile timeout in `GenerateAndCompile` is too short for an
  amalgamation of this size.

## 2. What changed

### Vendored dependency
- Official SQLite amalgamation **3.46.1** vendored at
  `runtime/sqlite/c/vendor/sqlite3.c` and `sqlite3.h`.
- Archive SHA-256:
  `77823CB110929C2BCB0F5D48E4833B5C59A8A6E40CDEA3936B99E199DBBE5784`.
- File hashes are pinned in `runtime/sqlite/c/vendor/README.md` and asserted
  by `TestSQLiteKarkFresh`.
- Only `sqlite3.c`/`sqlite3.h` are vendored; `shell.c` and `sqlite3ext.h`
  are not needed.

### Runtime and driver
- Small binding in `runtime/sqlite/c/karkain_sqlite.{h,c}` with five builtins:
  - `sqlite_open(path)` → handle int (0 on failure)
  - `sqlite_exec(handle, sql)` → status code (0 success)
  - `sqlite_query(handle, sql)` → array of rows, each row an array of cells
  - `sqlite_close(handle)` → status
  - `sqlite_last_error()` → `sqlite:`-prefixed string, empty on success
- Handles are bounded slot indices (64 max); raw `sqlite3*` pointers never
  become Karkain values.
- `runtime/sqlite/sqlite.go` embeds the amalgamation; the CLI writes it beside
  generated C and compiles/links it as an extra source when a program uses
  `sqlite_*`.
- POSIX links add `-ldl -lpthread`; Windows needs no new library.
- Compile timeout rises to 20 minutes only for SQLite programs.
- Split/incremental compilation falls back to the monolith C path for SQLite
  programs because the object flow does not model extra sources yet.

### Both engines
- Five names registered in Go resolver, kcc checker/sema and both C dispatchers.
- `needsSQLite` prescan gates emission in monolith and split paths.
- `stdlib/db/db.kark` keeps all 26 SQL-text functions and adds five
  `db_sqlite_*` wrappers: `db_sqlite_open`, `db_sqlite_exec`,
  `db_sqlite_query`, `db_sqlite_close`, `db_sqlite_error`.

## 3. Evidence

`pkg/cli/phase_v1222_sqlite_test.go` (`TestPhaseV1222_`) PASS 111.075s through
the real CLI:

- in-memory CREATE/INSERT/SELECT both engines: Go 31.06s, kcc 44.74s;
- temp-file reopen both engines;
- deterministic `sqlite:` error strings and invalid-handle close;
- DB-free generated C has no `karkain_sqlite_open(`;
- native K145 refusal with no image.

A first gate draft used the same temp-file database for both engines, so the
kcc leg saw the Go leg's table and inserted a second row. Each engine now gets
its own per-engine file; that is a harness isolation fix, not a compiler fix.

## 4. Non-claims and boundaries

- **C23 only.** Native has no FFI/C-import path or SQLite linkage and refuses
  by name; WASM remains K108-gated.
- **No byte-identity** with the Go native backend; it cannot run SQLite.
- **No KIR pin value measured or predicted locally.** CI must measure
  `text=N verify=N` before re-pinning.
- No connection pooling, prepared-statement wrappers, bindings,
  transactions-as-values, ORM, or web/database framework. `sqlite_exec` takes
  complete SQL strings.
- The SQL-text `std.db` engine is untouched; both engines are available side
  by side and the driver is opt-in via `db_sqlite_*`.

## 5. CI

Two dedicated steps are wired in `.github/workflows/ci.yml`:
*Run SQLite runtime freshness gate* (`TestSQLiteKarkFresh`) and
*Run v1.2.22 real SQLite driver gate* (`TestPhaseV1222_`). The gate is a test
file plus a CI step, per the repository rule.
