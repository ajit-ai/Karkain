# v1.2.4 — CI hygiene: the exit-143 class is a runner shutdown

Status: **COMPLETE (corrective CI change; not a new increment and not a new
gate)**. Branch `feature/v1.2.4-native-trim`, version v1.2.x.

## The measurement

PR #14 (`develop -> main`, run `44979568391`) and its `develop` push twin
(`44979482671`) showed three red jobs:

| Job | Conclusion |
|---|---|
| `kcc whole-tree DIAGNOSTIC (informational)` | failure |
| `B2 seed closure (discovery, non-gating)` | failure |
| `Increment 154 self-bootstrap (discovery, non-gating)` | failure |

Every **required** check was green in the same runs: `Test` (9m46s),
`Documentation`, `kcc whole-tree self-check (Phase 122)`,
`Native PE execution (windows)`, and all thirteen `Build (...)` jobs. The PR
reads `mergeable: MERGEABLE`, `mergeStateStatus: UNSTABLE` — unstable only
because non-required checks are red.

The decisive evidence is in the log of job `136905942874` (B2, run
`44923984397`, the first completed run that carried these jobs), at the point
of death:

```text
[run karkain-compiler1] still running after 135s
##[error]Process completed with exit code 143.
##[error]The runner has received a shutdown signal. This can happen when
the runner service is stopped, or a manually started runner is canceled.
```

The same two lines terminate `kcc whole-tree DIAGNOSTIC` (job
`136905942796`), which was killed inside Half 1 — the pure Go transpile
`go run ./cmd/karkain build src/compiler/main.kark` — before `gcc` ran at all.

This is **not** the memory guard and **not** gcc:

- the job's own first step printed `MemTotal: 16366632 kB`,
  `MemAvailable: 15203616 kB` — 15.2 GB free of 16.3 GB;
- `ci.yml` has **no** `concurrency:` block, so no newer run cancelled these
  jobs (`grep -E '^(concurrency|  group|  cancel-in-progress)'` returns
  nothing);
- the job conclusion is `failure`, not `cancelled`, and the runner agent
  itself emits the shutdown line.

Exit 143 is `128 + SIGTERM`, delivered by the runner agent as the hosted VM is
reclaimed. It is the REL-002 class `PHASE-143-FINAL-REPORT.md` §F already
recorded (five consecutive runner deaths during the stage-2 transpile) — now
with the terminating line captured, which the earlier records could not show.

## What changed

1. **`kcc-whole-tree-diag` is removed.** It was a self-declared *one-off*
   diagnostic whose question was "is the exit-143 kill the kcc build (gcc) or
   the whole-tree self-check?". Both halves of that question are now answered
   by evidence from a sibling job: neither. The job never reached its
   `Interpret` or `Upload observations` steps in any run — every run skipped
   them because the runner had already gone — so it has never produced a
   single observation. Keeping it would keep burning ~5 minutes per run to
   collect nothing.

2. **`B2 seed closure` and `Increment 154 self-bootstrap` run on `schedule`
   and `workflow_dispatch` only.** New trigger:

   ```yaml
   schedule:
     - cron: '0 4 * * 0'   # Sunday 04:00 UTC, on the default branch
   ```

   and each job carries

   ```yaml
   if: github.event_name == 'schedule' || github.event_name == 'workflow_dispatch'
   ```

   `workflow_dispatch` keeps a manual attempt available immediately after any
   infrastructure change, without waiting for the week.

## What is NOT weakened

Both proofs still exist, still run, and still fail hard. Their verification
steps are unchanged: a missing log, `--- SKIP:`, any `FAIL`, a missing
`stage2 == stage3 bitwise identical` witness line, or a witness line with a
zero byte count are all failures. The only thing removed is the *frequency* of
runs that were dying before the proof could start.

**Nothing is proven that was not proven before.** Increment 154's conditions
5-6 and B2 remain **UNPROVEN** and stay carried to v1.3.0 as UNMET. This change
records the blocker; it does not close it.

## Verification of this change

- `npx js-yaml .github/workflows/ci.yml` parses cleanly.
- Job count 10 (was 11); `kcc-whole-tree-diag` absent.
- `on:` now lists `push`, `pull_request`, `schedule`, `workflow_dispatch`.
- Both guarded jobs report the expected `if:` expression.
- Diff is `26 insertions(+), 120 deletions(-)` — one job removed, two guards
  and one schedule added, no other job touched.

## Effect on PR boards

A push or PR can no longer show red for a runner shutdown. The three jobs that
remain invisible on every push are exactly the three that GitHub was killing;
the gates that actually decide whether the tree is shippable are unchanged.
