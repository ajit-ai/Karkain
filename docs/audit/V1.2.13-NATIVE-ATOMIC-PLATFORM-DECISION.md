Date: 2026-11-25

## 1. Platform decision

The C-free native target has **no atomic primitives** — no `lock` prefix,
no `cmpxchg`, no memory fences. Consequently `@atomic_load`,
`@atomic_store`, `@atomic_fetch_add`, `@atomic_fetch_sub`,
`@atomic_exchange` and `@atomic_cas` are **deliberately unavailable** on
`native-x86_64-*` and are refused BY NAME with `error[K145]`. The C23
path keeps the full `@atomic_*` surface via C11 `<stdatomic.h>`.

This is a **capability decision, not a gap**: implementing atomics on the
native target would require lock-prefix instructions, `cmpxchg`, and
memory fences in the self-hosted emitter — a substantial piece of work
that the native backend does not carry. Until that layer exists, atomics
stay on the C23 path.

## 3. What this does NOT claim

- No native atomic implementation. Native target = write + exit only.
- No litmus goldens on native (atomics are C23-only).
- No byte-identity claim. No kcc native parity claim.
