# v1.2.34 follow-up — dynamic-library boundary (baseline + decision)

Status: **BASELINE / DECISION**. The builtin/stdlib slice is complete (PR #68),
signal control was added as a follow-up (PR #73), and
`V1.2.34-TAKEOVER-BASELINE.md` §5 names the dynamic-library boundary as the
remaining item. This slice decides and pins that boundary. It adds **no new
runtime and no new language builtin**.

## 1. Measured current state

- `pkg/jit/ffi.go` has an `FFIRegistry` with `LoadLibrary` / `ResolveSymbol` /
  `UnloadLibrary`, but the platform layer is explicitly a stub:
  - `dynamicLoad(path)` returns `0` with no error (no OS handle);
  - `dynamicSymbol(handle, name)` **always** returns
    `ffi: dynamic symbol resolution not available (use simulation)`;
  - `nativeCall(sym, args)` **always** returns
    `ffi: native call not available (use simulation)`.
- The working path is `FFILib.RegisterSymbol`, which inserts a symbol into the
  registry's in-memory map. That is a **simulation**, not a loaded library.
- No `.kark` source can reach this registry: there is no `dlopen`/`dlsym`/
  `dll_open` builtin in either engine's resolver/checker tables, and the Go
  resolver reports an undefined function for such calls.
- The supported interop surface is static C FFI: `import "C" { ... }` blocks are
  preserved by both front ends and emitted as C declarations at build time.

## 2. Decision

| Target | Dynamic library loading | Evidence |
|---|---|---|
| `native-x86_64-*` (C-free) | **Not supported.** The image has no dynamic loader and imports only the kernel32 exports its own bootstrap resolves. | `TestPhaseV1234D_NativeDynlibRefused` |
| C23, Go and kcc engines | **Not supported.** There is no dynamic symbol lookup from a `.kark` program. `import "C"` blocks are still accepted at the syntax level. | `TestPhaseV1234D_NoLanguageDynlibBuiltin` + `TestPhaseV1234D_StaticCInteropSyntaxAccepted` |
| WASM | **Not supported** (existing K108 boundary; unchanged). | unchanged |
| `pkg/jit` registry | **Simulation only.** `Handle == 0`, real symbol resolution and native calls always fail; only manually registered symbols resolve. | `TestPhaseV1234D_JITDynamicLoadingIsStubbed` |

The gate's JIT layer has a **positive control**: a manually registered symbol
resolves successfully. Without it, an "always fails" assertion would be
satisfied by a registry that fails at every step, which reads exactly like the
boundary being proven.

## 3. Boundaries

- This is a **decision and a pin**, not an implementation of dynamic loading.
  Implementing real `dlopen`/`dlsym` plus a callable function-pointer type would
  be a new increment with its own baseline and gate.
- No new builtin, no new link library, no change to `src/compiler/*.kark`.
  Therefore **the whole-tree KIR pin does not move** and must not be predicted
  or re-pinned by this slice.
- BSD remains unproven (no runner), consistent with the rest of the project.

## 4. Evidence rule

Every "not supported" row is paired with an observable assertion, and the one
in-process layer (the JIT registry) carries its own positive control. A gate
that only greps for the absence of a symbol would pass on any compiler and
prove nothing.

## 5. Separate finding — static C FFI calls are NOT proven to link

An earlier draft of this gate tried to use a typed call
`import "C" { func abs(x int) int } ... print(C.abs(-7))` as the positive
control for "the supported interop path works". **Measured, it does not:**
`karkain build --engine go --target x86_64-windows -c` emits a generated C file
containing both a leftover `print(C.abs(-7))` statement and a call
`abs(karkain_negate(make_int(7)))` that passes a `Value` where libc's `abs`
expects an `int`. gcc rejects it with `expected ')' before '.' token` and
`incompatible type for argument 1 of 'abs'`.

This is a real, separate defect in the C-interop call lowering — not the
dynamic-library boundary — and it is **not fixed by this slice**. The gate's
positive control was therefore narrowed to the honest claim: `import "C"`
blocks still parse without errors (`TestPhaseV1234D_StaticCInteropSyntaxAccepted`).
No claim is made that a typed C call links or runs. This finding is recorded
rather than silently dropped, so a later reader does not assume static FFI is
verified just because its syntax is.
