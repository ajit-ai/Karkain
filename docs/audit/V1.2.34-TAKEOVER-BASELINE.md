## 2. Measured defect blocking the slice

A program `import std.env; print(env_get("KARKAIN_PROBE_VAR"))` fails on BOTH
engines:

- Go: `error[K002]: undefined function 'env_args'` at the stdlib wrapper
  (`stdlib/env/env.kark:72`).
- kcc: `error[K101] line 72: undefined function 'env_args'`.

Root cause: the WIP added the C runtime and the generated mirror, but **never
registered the builtins** in either engine's semantic table or call dispatch.
`pkg/sema/resolve.go:builtinNames`, `src/compiler/checker.kark`,
`src/compiler/sema.kark` and both codegen call sites do not know these names.

A second defect is structural: each stdlib wrapper has the same name as the
builtin it calls (`string env_get(...) { return env_get(name) }`). Since Go
codegen dispatches user functions before builtins (Phase 83 shadowing rule),
registering `env_get` as a builtin under that name would make the wrapper call
itself recursively. The integration must give the builtins distinct internal
names (`osctl_*`) while keeping the public stdlib API unchanged.

## 3. Integration plan

1. Rename the **builtin calls** inside the four stdlib modules to `osctl_*`;
   keep every public function name and signature intact.
2. Register the 13 `osctl_*` builtins with arities in both engines:
   `pkg/sema/resolve.go` + `pkg/codegen/codegen.go` (Go), and
   `src/compiler/{checker,sema,codegen}.kark` (kcc). Map each to the existing
   `karkain_<name>` C helper.
3. Name the native/WASM boundary explicitly: these builtins are C23-only and
   must be refused by name on native (`error[K145]`) and WASM (`error[K108]`).
4. Write a real both-engine CLI gate plus a CI step; update SPEC.md,
   stable-api.rst, feature-matrix.rst, native-feature-matrix.json, the v1.3.0
   checklist row and the AGENTS completion record.

## 6. Portability

Win32 and POSIX implementations ship in the same C runtime; the generated kcc
mirror is a single file emitted only on use. Native and WASM are explicitly
refused, so no platform silently mis-compiles these builtins. BSD remains
unproven (no runner), consistent with the rest of the project's platform
policy.

## 7. First-CI corrective (PR #68)

Two Linux-only defects, both found by CI and neither a compiler logic error:

1. **chmod declaration conflict.** The A1 byte writer declared
   `extern int chmod(const char*, int);` unconditionally; glibc's
   `<sys/stat.h>` declares `int chmod(const char*, __mode_t)`, so the generated
   C failed with `conflicting types for 'chmod'`. Fixed in **both** preambles:
   the declaration is now inside `#ifdef _WIN32`, with `<sys/stat.h>` included
   on POSIX. Verified in generated C from the Go front end (lines 700–703) and
   from kcc itself (`p.c23` lines 139–142). Karkain strings do not expand `\n`
   in emitted C, so the guard is five separate `emitLine` calls in
   `src/compiler/codegen.kark`.
2. **Gate target selection.** The native-refusal gate always used
   `native-x86_64-windows`; on Linux the CLI's cross-run guard refuses first
   with a build-only hint, so the native backend was never asked and the
   K145/K108 assertion failed. The gate now uses `a1HostTarget()` so the
   request reaches the lowering path on the host that runs it.

KIR pin history from CI measurements only: 20494 → **20933** (the takeover's
builtin wiring), then → **20938** (the corrective's five `emitLine` calls).
Both assertion sites in `phase122_pipeline_ownership_test.go` and
`phase151a5_win_test.go` now read **20938**, measured on the PR #68 Phase 122
job (`text=20938 verify=20938`); no value was predicted locally.

## 8. Second CI corrective — v1.2.19 cross-gate regression

A later PR #68 run failed `TestPhaseV1219_MetricsBothEngines/go` on Linux,
which imports `std.os` (a v1.2.19 module the takeover edited):

- `Value karkain_user_os_kill(Value int);` — `two or more data types in
  declaration specifiers`. The three new wrappers were written as
  `func os_kill(int pid)`, which the parser reads as a single parameter named
  `int`, leaving `pid` undeclared in the body. Fixed to type-first form
  `int os_kill(int pid)` (and likewise `os_spawn`, `os_wait`).
- `implicit declaration of 'karkain_proc_spawn'` — the Go prescan
  `isOSCtlBuiltin` still listed the old public names and not the internal
  `osctl_*` names the wrappers now call, so `needsOSCtl` never became true.
  Fixed by recognising all 13 `osctl_*` names.

Verified locally: `TestPhaseV1219_` and `TestPhaseV1234_` both PASS (69.105 s)
with a freshly built CLI. This is why the takeover keeps the pre-existing gate
in the regression set — a stdlib edit can break a different version's gate.
