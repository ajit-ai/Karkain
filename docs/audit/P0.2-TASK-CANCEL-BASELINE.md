# P0.2 — Task cancellation and timed joins

**Status: COMPLETE for the slice.** Baseline and measured evidence for
`cancel(task)` and `join_timeout(task, ms)` on both engines. No scheduler
redesign, no preemption, no P0.3 work.

Date: 2026-11-23
Branch: `develop` (working tree; nothing committed for this slice)
Base commit: `5b89aa7` (v1.2.5c)

---

## 1. What was missing

`join(task)` existed (Phase 107) and blocks until the task finishes. There was
no way to bound that wait and no way to abandon work that had not started, so a
program whose result was no longer needed either blocked forever or had to
poll application-level state. This slice adds exactly two builtins and one
scheduler field.

## 2. Contract

| Call | Returns | Semantics |
| --- | --- | --- |
| `cancel(task)` | `bool` | `true` on the first accepted request; `false` for a null/completed/already-cancelled/non-task handle. Repeated calls are safe. |
| `join_timeout(task, ms)` | `bool` | `true` if the task completed within the budget, `false` on timeout. Never cancels. The task stays joinable. `0` is a non-blocking completion check. |

Cancellation states:

* **Queued** — the task never runs. `karkain_run_task` checks the request at
  entry and finishes the task with `KARKAIN_TASK_CANCELLED` (`-4`), so
  `join` reports `-4` and the body's side effects do not happen.
* **Running** — cooperative only. The request is recorded and the task is
  broadcast awake, but the body is not interrupted; whatever it returns
  stands. A program that wants to observe the request must check it itself.
* **Completed** — not cancellable (`false`), and its result is unchanged.

Timing: `karkain_monotonic_ms()` (`GetTickCount64` on Windows,
`CLOCK_MONOTONIC` elsewhere) provides a deadline; each wait iteration
recomputes the remaining budget and waits on the task's condition variable.
There is no spin loop. A negative remaining budget returns `0`.

Invalid input is safe rather than fatal: a null handle is `false` from both
calls, and a negative timeout is `false` from `join_timeout` and leaves the
task untouched. A **literal** negative timeout is additionally a compile-time
diagnostic (see §4), because a constant mistake should not become a runtime
surprise.

## 3. Implementation

C runtime (`runtime/concurrency/c/`):

* `karkain_conc.h` — `KARKAIN_TASK_CANCELLED (-4)`, `long cancel_requested`,
  and the two new declarations.
* `karkain_scheduler.c` — `karkain_monotonic_ms`, `karkain_task_cancel`
  (CAS-based single-request flag; broadcasts), `karkain_task_join_timeout`
  (null/negative rejection, monotonic deadline, no cancellation), and the
  queued-task skip at the top of `karkain_run_task`.
* `KARKAIN_WORKERS` already existed and is used by the gate to force a
  deterministic single-worker queue.

Go engine:

* `pkg/sema/resolve.go` — `cancel` / `join_timeout` in `builtinNames`, arity
  diagnostics, and a literal-negative-timeout diagnostic.
* `pkg/codegen/conc_runtime.go` — `concBuiltin` extended, the two Value glue
  functions, and `genConcCall` dispatch.

kcc engine:

* `src/compiler/checker.kark` — `isCheckerBuiltin`, `checkerBuiltinArity`
  (`cancel` → 1, `join_timeout` → 2), and quoted-actor validation (§7).
* `src/compiler/sema.kark` — builtin and arity tables.
* `src/compiler/codegen.kark` — `concIsBuiltin`, glue emitters, and
  `emitConcCall` branches.
* `src/compiler/conc_runtime.kark` — regenerated from the C runtime by
  `scripts/gen-conc-runtime.ps1`; never hand-edited.
  `TestConcRuntimeKarkFresh` verifies the embedded copy matches the source.

## 4. Diagnostics added

| Condition | Engine | Message shape |
| --- | --- | --- |
| `cancel()` arity ≠ 1 | Go | `cancel() takes 1 argument (a task handle)` |
| `join_timeout()` arity ≠ 2 | Go | `join_timeout() takes 2 arguments (a task handle and a non-negative millisecond timeout)` |
| literal negative timeout | Go | `join_timeout() timeout must be non-negative` |
| arity ≠ expected | kcc | `error[K104] builtin '<name>' expects N arguments but got M` |

Exit code is 3 (compile/type/semantic) on both engines.

## 5. Gate

`pkg/cli/phase_p02_task_cancel_test.go` (`TestPhaseP02_*`). The CLI and the
self-hosted compiler are each built once per process (`sync.Once`); the kcc
binary is copied out of the test-owned temp dir so later cases do not see
`KARKAIN_KCC points to missing binary`. Engine selection for a run is the
test-only `KARKAIN_P02_ENGINE` value (`go` or `kcc`), because a single
combined run of both engines is unreliable on a ~4 GB host.

| G `InvalidHandlesAndArgs` | null handles and computed negative timeout are safe | `false\nfalse\nfalse\n0\n` |

Per-engine result (measured on this host):

```
KARKAIN_P02_ENGINE=go  go test ./pkg/cli -run TestPhaseP02_ -count=1   PASS 38.6s
KARKAIN_P02_ENGINE=kcc go test ./pkg/cli -run TestPhaseP02_ -count=1   PASS 57.4s
```

Test D forces `KARKAIN_WORKERS=1`; run queues are LIFO, so a single worker
plus a channel rendezvous is what makes "still queued when `cancel` runs"
provable rather than likely. Readiness is expressed as
`print(receive(ready))` (prints `1`) instead of an unused `let`, so the
synchronisation point is observable and does not produce an unused-variable
warning.

## 7. The kcc actor gap this slice closed

`TestPhaseP02_I_ActorRegression` passes `actor(handler, 0)` (an identifier, not
a quoted name) and expects a compile error. The **Go** resolver already
rejected that form (P0.1) because it lowers to `mk_nil()` and the first
`actorSend` dereferences it as a pointer, producing `0xc0000005`. The kcc
checker did **not** validate the argument, so the same program compiled under
kcc and crashed at runtime.

`src/compiler/checker.kark` now applies the same rule: `actor()` with zero
arguments or a non-string first argument is `error[K104]` with the message
naming the quoted-handler requirement. This is a narrow parity fix inside
P0.2, not new scope, and it is recorded here because it changes what kcc
accepts.

## 9. Boundaries stated, not implied

* **No preemption.** A running task is not interrupted. `cancel` on a running
  task is a recorded request; the body's result stands. This is deliberate:
  preemption would be a scheduler and stack-ownership redesign.
* **`-4` is the cancelled status.** `join` on a cancelled queued task returns
  `KARKAIN_TASK_CANCELLED`; no new exit code is introduced.
* **No new channel/actor surface.** `spawn`, `join`, `channel`, `actor` and
  the send/receive calls are byte-for-byte unchanged (Phase 137 goldens still
  pass).
* **KIR pin not predicted.** `src/compiler/conc_runtime.kark` is regenerated,
  so the whole-tree KIR count moves. Local whole-tree verification crashes on
  this host (the documented class), so the pin stays **17095** and the value
  is taken from the CI measurement, never guessed. This is the same procedure
  v1.2.5a/b/c used.
* **Host capacity, not regressions.** `TestPhaseV125C_` and the later
  `TestPhaseV124_` cases failed in combined runs with
  `stage-1 link failed: exit status 1` /
  `cc1.exe: out of memory allocating 65536 bytes`, and one V125C run was
  killed at 33 minutes. That is the documented ~4 GB OOM class
  (`.p02-v125c.log`), not a P0.2 regression: this slice touches the
  concurrency runtime and two builtins, and the V124/V125C gates exercise the
  native codec helpers.
