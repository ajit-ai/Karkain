### 1.1 Why `TYPE-FOUNDATION` has no number yet

`KARKAIN-VERSION-PLAN.md` §3 gives v1.3.0 the increments **155, 156, 158–161**
and reserves **181–184** for post-2.0. §9 says "154+ are proposals — a number is
assigned only when an increment is scheduled." The type-system foundation was
informally proposed as **181**, which would consume a reserved post-2.0 slot for
work scheduled *before* 2.0. Rather than resolve that by silently renumbering
either the reservation or the work, this checklist records the item under a
working label and leaves the number to the scheduling decision. **No number is
invented here**, and 181–184 stay reserved.

## 2. Closure conditions — the release ships only if ALL hold

Recorded at freeze and **not edited afterwards**. Status lives in §2.1, never in
a reworded condition.

1. `std.path`, `std.env`, `std.time`, `std.random` and `std.json` ship on **both** engines
2. **native function-call lowering** exists and a genuine `import std.*` program **builds and executes** through the C-free native path *(carried from v1.2.0 Condition 2)*
3. a native networking capability exists with an **explicit platform-support decision**, and a real `std.net` program builds and runs without a C compiler **on each platform claimed as supported** *(carried from v1.2.0 Condition 3)*
4. package management and scaffolding are **owned by kcc**, not the Go engine
5. generics v2 (`Deque[T]`, `Set[T]`) and `const` folding ship
6. **linear types are enforced** — proven by negatives on both engines
7. the atomic surface ships with **litmus goldens**
8. **zero** Go-engine-only core rows in the feature matrix
9. `stage2 == stage3` with **no Go toolchain** for the self-bootstrap closure *(carried from v1.2.0 Conditions 5–6)*
10. the full version QA battery passes (units, Phase-114 corpus on both engines, conformance, probes, every gate file, Sphinx `-W` + linkcheck, `verify-examples`, `install`/`verify-install`, `rc-journey`)

**These are not weakened to close.** A version is not closed as "green
except X": an unmet condition moves to the next version or to an explicit,
written carry-over list (§4). §2.3 of `v1.2.0-CHECKLIST.md` is the precedent,
and it exists because carrying work out is a recorded owner decision, never an
inference from a skip.

## 3. Close ceremony

Unchanged from `v1.2.0-CHECKLIST.md` §3 and `AGENTS.md`:

**Per increment:** code + gate + audit note + `AGENTS.md` record → commit
`develop` → merge `main` → push. The push fires `ci.yml`; the `main` push also
fires `docs.yml` (Sphinx `-W` + Pages).

**At version close:** checklist finalised → full QA battery → version identity
(`VERSION`, both Go banners, three kcc banners, generated headers, LSP, every
version-pinning test) → docs flip → final `develop` → `main` merge + push →
**tag `v1.3.0` (owner-only)** → GitHub Release → post-publish verification
against the *shipped* binary.

**Owner-only, not doable from the repo:** the tag, registry visibility, and
code-signing identities.

## 5. Governance

* **A completed increment is frozen.** A later defect does not reopen it; a
  corrective change is recorded against the frozen baseline with the owning
  layer, the demonstrated failure, the downstream effect and the affected
  gates (`AGENTS.md`, Governance).
* **Evidence discipline.** A gate that can pass without comparing anything is
  not evidence. A skip is **not** a pass: any skip-when-unproven arrangement
  must record the claim as **open**, never as satisfied.
* **A gate is a test file *plus* a `ci.yml` step.** Writing and running a gate
  locally is not sufficient.
* **Scope freezes when the version opens**; ideas go to the next version or to
  an explicit carry-over list.
* **Heavy gates are never combined** in one command (the ~4 GB host rule).
* **A KIR pin is measured, never predicted.** If it cannot be measured, the pin
  gate stays honestly red rather than green on a guess.
