## 1. Purpose

This contract defines the boundary between what Karkain **guarantees**, what it
**implements**, and what it **does not support**. It is the single reference that
every backend, every runtime, and every tool must agree on. Without this
contract, each backend evolves independently and "implemented" becomes
indistinguishable from "supported."

This document is a **contract**, not a roadmap. It states what is true today and
what must remain true. It does not promise future work.

## 2. Language semantics and supported constructs

### 2.1 Core language

Karkain is a statically typed, imperative systems programming language with
manual memory management (no garbage collection in the safe subset).

**Supported constructs (v1.2.0):**

| Construct | Status | Notes |
|---|---|---|
| Variable declarations (`let`, `var`, `const`) | Supported | `let`/`var` mutable, `const` immutable |
| Type annotations | Supported | Explicit types; type-first syntax (`int x = ...`) |
| Functions | Supported | Parameters, return values, recursion |
| Generics (v1) | Supported | Explicit type args with `[]`: `f[int](x)`; no inference; constraints parse but unchecked |
| Closures / first-class `fn` | Supported | `fn` values, captures by reference, `IndirectCallExpr` |
| Structs (records) | Supported | Fixed layout, field access, by-pointer passing |
| Enums (tag-only) | Supported | `EnumName.Variant` patterns; no payload destructuring |
| Arrays | Supported | Fixed-size, index access, `for-in`, `push()` (arena-allocated) |
| Maps | Supported | Linear-scan entries, int keys in v1 |
| Strings | Supported | Immutable, length-prefixed, concat/slice/compare |
| Control flow | Supported | `if`/`else`, `while`, C-style `for`, `break`, `continue`, `match` |
| Pattern matching | Supported | `match` on enum tags; `_` wildcard |
| Error propagation | Supported | `?` operator (kcc parity) |
| Concurrency | Supported | `spawn`, `channel`, `actor`, `receive` |
| Modules/imports | Supported | `import std.x`, sibling file assembly |
| C interop | Supported | `import "C" { ... }` |

**Not supported (explicitly):**

| Construct | Status | Notes |
|---|---|---|
| Traits/interfaces | Not supported | No trait/impl syntax |
| `Result`/`Option` types | Not supported | Planned |
| Compile-time evaluation | Not supported | Planned |
| Reflection | Not supported | Planned |
| Payload enum destructuring | Not supported | Tag-only match |
| `for-in` on native target | Not supported | Refused by name in native driver |
| Float statements on native target | Partial | Int statements only; float expressions in print/return work |

### 2.2 Type system

- **Primitive types:** `int`, `float` (float64), `bool`, `string`
- **Composite types:** arrays `[T]`, maps `map[K]V`, structs, enums
- **Type annotations are strings in the AST** (`VarDeclStmt.Type string`). Type values do not exist at runtime.
- **No type inference** for generics (explicit type args required).
- **Constraints** parse and store but are unchecked (no trait/impl syntax to declare against).
- **Mutability:** `let` and `var` are both mutable; `const` is immutable. (LANG-001/002 open design decision.)

### 2.3 Memory model

- **No garbage collection.** Manual memory management via `alloc`/`free` (freestanding runtime) or arena bump allocator (native target).
- **Native target arrays:** fixed-footprint frame values sized by layout pass; `push()` allocates from a compile-time-bounded arena.
- **Strings:** immutable, length-prefixed, stored in `.rodata` for literals; arena-allocated for concatenation results.
- **Structs:** field area follows the slot; fields laid out in declaration order (int/float = 1 unit, string = 2 units, 8-byte aligned).
- **No ownership or borrow checking.** The borrow checker (`pkg/sema/borrow.go`) exists but enforces lexical scoping only (Phase 51). Full ownership/borrow model is a v1.3.0 objective.

## 3. Memory and concurrency safety guarantees

### 3.1 Current state

Karkain does **not** provide memory safety guarantees in v1.2.0. The language
has no ownership model, no borrow checker enforcement across function calls,
and no lifetime analysis. The borrow checker (`pkg/sema/borrow.go`) tracks
lexical scoping and use-after-scope-end diagnostics only.

### 3.2 What Karkain does provide

- **Bounds checking:** Runtime checks for array/string index out of range (native target: `Int3` trap; C23 path: `karkain_checked_get`/`set` with `runtime error: index out of range at <file>:<line>`).
- **Checked arithmetic:** Division/modulo by zero produces `runtime error: division by zero at <file>:<line>` (both engines).
- **Stack traces:** Runtime errors include frame dumps (`karkain_frame_enter`/`leave`/`set_line`).
- **Concurrency primitives:** Channels and actors are implemented in the C runtime with proper synchronization.

### 3.3 Safe subset definition (v1.3.0 target)

The safe subset will be defined in `docs/architecture/V1.3-MEMORY-SAFETY-DESIGN.md`.
Until that document exists, **no safe subset is claimed**. Programs using
`alloc`/`free`, raw pointers, or `unsafe` blocks are explicitly outside any
safety guarantee.

### 3.4 Concurrency safety

- **Channels:** Bounded and unbounded, blocking send/receive, deterministic close-drain.
- **Actors:** Serialized dispatcher jobs over a mailbox with state-cell box.
- **Spawn/join/wait_all:** Work-stealing task scheduler.
- **No data-race detection.** Shared mutable state across tasks is the programmer's responsibility.

## 4. KIR specification and backend responsibilities

### 4.1 KIR v1 text format

KIR (Karkain Intermediate Representation) is a deterministic, line-oriented,
depth-indented rendering of the parsed AST. It is emitted by `kirEmit` in
`src/compiler/kir.kark` and verified by `kirVerify`.

**Structural contract:**
- Exact `KIR v1` header line
- `source: <basename>` line (path-location-independent)
- Two-space indentation per nesting level, monotone +1
- ` line: <decimal>` statement suffixes (exempting bare `block` introducers and `stmt <type>` fallbacks)
- Bare `block` introducers have no line suffix

**KIR does not feed the native backend.** The native driver consumes the parsed
AST directly. KIR is a verification artifact: it proves the compiler's own
source parses and type-checks, and provides a deterministic dump for debugging.

### 4.2 Backend responsibilities

| Responsibility | C23 backend | Native backend |
|---|---|---|
| Input | Parsed AST (via Go or kcc) | Parsed AST (via kcc driver) |
| Value model | Tagged `Value` struct (int/float/bool/string/array) | Unboxed, statically kinded (frame slots) |
| Memory management | C heap (malloc/free) | Frame slots + bump arena |
| Concurrency | C runtime (`runtime/concurrency/c/`) | Not yet supported on native target |
| Error reporting | `karkain_runtime_error` with file:line | `Int3` trap (bounds); diagnostic via reporter (where supported) |
| Output | C23 source → gcc/clang/cl | ELF/PE/Mach-O binary |

### 4.3 Backend contract

Both backends must implement the same language contract for the **supported
subset**. Unsupported constructs must be refused explicitly (K145 on native
target) rather than silently routed through another backend.

The native target's supported subset is documented in the refusal table of
`src/compiler/native_value.kark`. A construct is either:
- **Supported:** lowered and executed with evidence.
- **Refused by name:** `error[K145]: native target: <construct> is not lowered by the native driver`.

There is no third category.

## 5. Runtime and ABI specifications

### 5.1 Calling convention (native targets)

- **Registers:** RDI, RSI, RDX, RCX, R8, R9 (first 6 units)
- **Units:** 8 bytes each. int/float/bool/struct/map = 1 unit; string/array = 2 units (ptr + len)
- **Extras area:** units beyond 6 are staged in caller frame at `extrasBase`, addressed by R10
- **Return value:** RAX (int/float/bool/struct/map); string returns (RAX=ptr, RDX=len)
- **Frame layout:** locals → recArgAreas → binTemp (64×8 bytes) → strTemp (5×64×8 bytes, conditional) → mapStage (8 bytes, conditional) → extrasBase → Windows 16-byte rounding → +96 bytes (argSpillBytes, 6×16)
- **Callee-saved:** R12–R15 (Phase 150C register allocation, opt-in via `KARKAIN_NATIVE_REGALLOC=1`)
- **Alignment:** 16-byte on Windows (entry `and rsp, -16`); Linux/macOS enter with `rsp%16==8`

### 5.2 C23 backend ABI

- Standard C calling convention (platform default).
- `Value` struct: tagged union (int/float/bool/string/array).
- Runtime: `karkain_runtime_error()`, `karkain_checked_div/mod/get/set()`, frame tracking.

### 5.3 System call conventions

| OS | write | exit |
|---|---|---|
| Linux | 1 | 60 |
| macOS | 0x2000004 | 0x2000001 |
| Windows | kernel32 `WriteFile` (via PEB bootstrap IAT) | kernel32 `ExitProcess` |

### 5.4 Container formats

| Format | Status | Evidence |
|---|---|---|
| ELF64 (Linux) | Qualified (executed on CI) | `pkg/native/elf.go`, Phase 145–150 gates |
| PE32+ (Windows) | Qualified (executed on dev host) | `pkg/native/pe.go`, Phase 149–150 gates |
| Mach-O PIE (macOS) | Structural only | `pkg/native/macho.go`, Phase 149–150 gates (no macOS runner) |

### 5.5 Runtime error model

- **Format:** `runtime error: <kind> at <file>:<line>`
- **Exit code:** 1
- **Stack trace:** `stack:` dump with `function:line` frames (max 128 frames)
- **Checked operations:** division by zero, modulo by zero, array/string index out of range
- **Native target:** `Int3` trap for bounds violations (diagnostic via reporter where supported)

## 6. Supported target platforms and limitations

### 6.1 Qualified targets (v1.2.0)

| Target | Status | Evidence |
|---|---|---|
| `native-x86_64-windows` | Qualified (executed on dev host) | PE images run, print correct output, exit 0 |
| `native-x86_64-linux` | Qualified (byte-identical to Go oracle; executed on CI) | ELF images, CI Linux leg |
| `native-x86_64-macos` | Structural only | Mach-O PIE with rebase stream; no macOS runner exists |
| `wasm32-wasi` | Qualified (executed via wasmtime) | Phase 108 gate |
| C23 (any host with gcc/clang/cl) | Qualified | All phases |

### 6.2 Future targets (not qualified)

| Target | Status |
|---|---|
| `aarch64-linux` | Planned (cross-compilation mechanism exists; no native emitter) |
| `aarch64-windows` | Planned |
| `aarch64-macos` | Planned |
| `riscv64-linux` | Planned |
| Embedded systems | Longer-term |
| GPU targets | Experimental (WGSL emit only) |
| Quantum targets | Experimental (catalog entry only) |

### 6.3 Limitations (explicit, not defects)

- No C/Go toolchain independence yet (kcc build requires gcc + GMP + winsock).
- No FFI (foreign function interface) in the language.
- No `Result`/`Option` types.
- No traits/interfaces.
- No compile-time evaluation.
- No ownership/borrow model (safe subset not defined).
- No fuzz targets.
- No DAP debugger server.
- macOS Mach-O execution unverified (no runner).

## 7. Conformance, security, and performance acceptance tests

### 7.1 Conformance

- **Corpus:** 64 tests in 11 files (`conformance/`), run on both Go and kcc engines.
- **Phase 114 golden corpus:** 59 `.kark` files across 15 categories, byte-identical on both engines.
- **Probes corpus:** 11 golden-output programs enforced by `pkg/cli/probes_corpus_test.go`.
- **Native gates:** 30+ gate files in `pkg/cli/` and `pkg/native/`, each with a CI step.

### 7.2 Security

- **Current:** No fuzz targets, no SBOM, no signing, no dependency audit.
- **Planned (v1.3.0):** Fuzz targets for lexer/parser/sema, dependency audit, SBOM generation, reproducible builds.

### 7.3 Performance

- **Current:** One `BenchmarkNativeCompile` (11–53 µs/program). Phase 141 RSS table (kcc check 544.5 MB, `go build` 229.9 MB, gcc big-TU 484 MB).
- **Planned (v1.3.0):** Representative benchmark suite, published methodology, independent review.

### 7.4 Acceptance criteria for v1.3.0

The v1.3.0 release ships only if ALL of the following hold:

1. **Gate 1 — Safety:** No known unresolved critical memory-safety defects in the claimed safe language subset (safe subset must be defined first).
2. **Gate 2 — Parity:** Shared conformance tests pass for all officially supported native and C23 features.
3. **Gate 3 — Independence:** Clean-environment builds succeed without C/Go toolchains for explicitly supported targets.
4. **Gate 4 — Accelerator research:** GPU/quantum architecture documented, experimental prototypes clearly labelled.
5. **Gate 5 — Performance:** Benchmark results and methodology published, with independent reproduction or review documented.
6. **Gate 6 — Developer ecosystem:** Build/test/project/diagnostics commands qualified and documented.

"Green except X" is not complete. X moves to the next version or to an explicit carry-over list.

## 8. Version and scope governance

- **Version scope is frozen when the checklist is written.** New ideas go to the next version or an explicit carry-over list.
- **No long-lived version branches.** `main` stays shippable at all times.
- **Increment numbering:** 150+ are forward planning units. Numbers assigned when scheduled (per `KARKAIN-VERSION-PLAN.md` section 0).
- **v1.3.0 status:** PREPARED, not open. `VERSION` stays `1.1.0` until v1.2.0 is tagged. No v1.3.0 increment authorized until v1.2.0 tags.
- **SemVer:** Additive-only → MINOR. Anything removing/renaming stable syntax or changing stable signatures → MAJOR (2.0.0 earmarked for C-layout struct change).
